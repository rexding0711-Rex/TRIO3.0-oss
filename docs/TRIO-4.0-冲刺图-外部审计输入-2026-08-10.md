## 〇、TRIO 是什么（30 秒背景）

TRIO = 个人判断/决策辅助系统。九源数据 × 三引擎互证（DeepSeek/Kimi/GLM）→ 判断包（结论/推理链/来源/置信度/反证）→ 预测注册校准 → 越用越准的数据闭环。运行在 CLI（Claude Code 环境），种子轮融资中。

## 一、TRIO 3.0 现状（已盘点，事实）

### 3.0 已完成
- 25 斜杠命令 / 11 角色 / 11 场景 JSON / 32 记忆文件
- 数据闭环六环飞轮（采集→管道→决策→注册→验证→反哺）
- 判断包五要素：结论/推理链/来源/置信度/反证

### 4.0 能力已实现约 80%（分散在 scripts/ 和 state/）
| 能力 | 现状 |
|------|------|
| Runner 引擎 | `loop-engine.sh`（验证器/断点/停止条件完整）|
| 跨运行记忆 | `session_memory.py` + 32 记忆文件 + MEMORY.md 索引 |
| 知识自生长 | `kb-refresh.sh` + `prompt-self-optimize.sh`（evo-N 自改进）+ evolution/（4 记录）|
| 决策追溯 | `decision-log.jsonl`（35 条）+ `decision-outcome-loop.md`（对账协议 v1.1）|
| 质量仪表盘 | `run-history.jsonl`（57 条，含 eval_score 五维 + composite_score）+ `score_report.py` |
| 5.0 雏形 | `engine-gap-detector.py`（组合器原型）+ `sync_metrics.py` |

### 4.0 缺的 20%
1. **统一引擎调度**——能力分散在 scripts/，无单一入口串联
2. **事件驱动**——知识自生长是定时（kb-refresh）非 run 完成自动触发
3. **用户层**——无面向用户的可视化/留存机制（数码宝贝填补）

### 已知问题（DeepSeek 审计发现）
- 引擎使用率低：run-history 57 条中引擎引用为 0；prompt-self-optimize 从未 apply
- 运行层 7-15 后闲置近 1 个月（8 月无新 run）
- validator.py 是孤立文件（无脚本引用）

## 二、3.0 → 4.0 冲刺图（初稿，待裁决）

### 阶段一：引擎调度统一（2 周）
- 建 `engine-manifest.md`：8 项引擎能力 → 实际路径映射
- 建统一入口 `trio-engine.sh`：按场景调用 loop-engine/score_report/kb-refresh
- 补事件驱动：run 完成 → 自动触发知识沉淀

### 阶段二：决策闭环激活（2 周）
- decision-log 补验证状态字段（verified/falsified/pending）
- 让至少一个引擎真正接进 run 流程（loop-engine 全 workflow）
- 恢复运行层活跃度（8 月 0 run → 周均 2-3 run）

### 阶段三：数码宝贝上线（3-4 周）
- CLI 界面蛋 → 数码宝贝渲染
- 使用数据 → 经验值映射
- 进化分支（尽调/投资/知识 三路径）
- 与决策闭环绑定（校准验证 → 进化加速）

### 4.0 完成标志
- [ ] 一个完整场景无人干预跑到尾（含知识沉淀）
- [ ] 5 个 run 无 ESCALATE
- [ ] 数码宝贝 3 条进化路径各孵化 1 只
- [ ] 引擎被真实调用（run-history 引擎引用 >0）

## 三、数码宝贝概念（用户定义）

> **「一开始是一只蛋，在 CLI 界面里，后面随着用户的使用可以变成究极体（比如战斗暴龙兽）。」**

### 我的理解（待验证）
| 维度 | 设计 |
|------|------|
| 起点 | CLI 界面出现一枚蛋（ASCII art），TRIO 初始化时孵化 |
| 喂养 | 用户每次使用 TRIO（run/判断/校准/知识）→ 喂经验值 |
| 进化 | 蛋→幼年→成长→成熟→完全→究极（6 阶），经验值触发 |
| 分支 | 进化路径由使用模式决定：尽调多→形态A，投资多→形态B，知识多→形态C |
| 数据 | 完全来自真实使用（run-history/decision-log/知识增量）——使用量的可视化 |
| 究极体 | 如战斗暴龙兽：累计 N 次高质量 run + M 次校准验证 |
