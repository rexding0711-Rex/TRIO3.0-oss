## 二、核心设计原则

### 2.1 OS + App 分离

**TRIO 3.0 = 内核**。定义"怎么做"——认知方法、质量门禁、交付标准。不定义"做什么"。

**Branch = 应用**。每个 Branch 在具体领域执行 TRIO 3.0 的方法论，产出领域特定的交付物。

| | TRIO 3.0 (内核) | Branch (应用) |
|---|---|---|
| **角色** | 宪法 + 最高法院 | 地方法院 + 执法 |
| **核心问题** | "这个判断可靠吗？" | "这个领域的答案是什么？" |
| **输出** | 规则、门禁、方法 | 报告、决策、代码/原型 |
| **更新节奏** | 季度修订（教训吸收） | 持续迭代 |
| **范围** | 通用，跨领域 | 领域专用 |

### 2.2 双向反哺

```
Branch 实践 → 教训/错误模式 → 上浮到 3.0 内核 → 修订 CORE.md / 新增门禁
                                        ↓
                              其他 Branch 自动继承
```

**已有先例**：
- Investor 铁律 0（先算后写）来自 Stock 的汇率 10x 错误
- Stock 铁律 S2（PE 不可脱离利润结构）来自 63 只分析实战
- CORE.md「PDF 不用 Mermaid」来自 7/14 乱码教训
- CORE.md「终版报告格式铁律」来自蔚星科技用户两次提醒

### 2.3 Branch 间交叉复用

Branch 之间不通过 3.0 内核中转，可以直接互借方法论：

- Stock 的评分卡方法论 → Engineer 的技术方案评估
- Engineer 的失效模式分析 → Investor 的技术尽调
- Investor 的铁律体系 → Stock 继承（已在运作）

## 五、待评审的核心问题

以下是我们希望外部模型给出判断的关键架构问题：

### Q1: OS + Branch 分离是否合理？
当前 TRIO 3.0 同时承担"方法论定义"和"具体分析执行"两个角色。是否应该更彻底地分离——3.0 只定义规则，所有执行（包括分析执行）都下沉到 Branch？

### Q2: Branch 粒度如何控制？
当前有 Stock / Investor / Engineer 三个 Branch。未来可能出现更多（TRIO-Legal? TRIO-Medical?）。如何判断一个新领域应该成为独立 Branch vs 现有 Branch 的子模块？

### Q3: 铁律继承 vs 独立演进？
Investor 的铁律是 Stock 的基础，但两个市场的逻辑不同。继承太紧密会导致 Stock 被 Investor 的逻辑绑架，太松散会导致重复造轮子。这个平衡点在哪？

### Q4: TRIO-Engineer 应该有自己的铁律体系吗？
工程判断（"这个散热方案可行吗"）和分析判断（"这家公司值得投吗"）的底层逻辑是否相同？Engineer 是否应该直接继承 Investor 的铁律框架，还是需要完全不同的质量门禁？

### Q5: Branch 间冲突如何裁决？
假设 Stock 和 Engineer 对同一家公司的判断出现矛盾（财务健康 vs 技术不可行），3.0 内核应该扮演什么角色？是仲裁者、记录者、还是不管？

### Q6: 这个架构最大的盲区是什么？
从 TRIO 团队之外的视角看，这个设计最容易被忽略的问题是什么？
