## 一、缘起：为什么建这个

创始人 Rex 的核心动机：

> "人在跨身份体系的时候永远会有盲区。调研 MEMS 项目时必须深度研究红外特征和多光谱，否则就是低效甚至无效沟通。陶瓷 3D 打印项目也是——只知道大概不够。工程师不懂资本市场会错过杠杆。我只是不希望有盲区而已。"

这不是"追求全知"——那是进攻性的、以自我为中心的。这是"不希望有盲区"——防御性的、以跨域对话质量为重心的。

TRIO 的核心命题：**人在跨越身份边界时，盲区是结构性的——不是知识不够，是视角不重叠。** 一个工程师看不懂投资条款，一个投资者读不懂热阻曲线。他们不是不聪明——他们站在不同的坐标系里。TRIO 尝试的是让同一个人结构化地调用多个视角，并且知道每个视角看不到什么。

## 二、宪法：TRIO 3.0 内核

**宪法定义"怎么思考"，不定义"思考什么"。**

### 三根柱子（不可变基础）

| 柱子 | 核心机制 | 防什么 |
|------|------|------|
| **认知隔离** | 三角色（发散者 Kimi / 审计者 DeepSeek / 交付者 Claude）并行处理同一材料，互不可见输出。当前运行在单模型（DeepSeek V4 Pro）上，通过独立 system prompt 实现角色分化。目标架构：多模型独立权重，提供真正独立审计 | 群体思维 |
| **结构化怀疑** | 每个关键结论附带可证伪条件。少数派不被多数投票淹没。矛盾不取平均 | 自欺 |
| **自验证闭环** | 交付前自检 → 自行修正 → 再检 → 外部抽查 | 随机质量 |

### 通用门禁系统

所有 Branch 共享的交付前检查：致命缺口扫描、框架挑战、AI 痕迹清除、排版硬检查（10 项）、拓扑门禁（C1-C5）、文件落库铁律、文档生成管道。

### 上下文预算纪律

三层加载模型：L1 常驻（≤30% 上下文窗口）→ L2 任务触发加载（≤40%）→ L3 仅索引不加载（≤30%）。防止规则膨胀吞噬认知带宽。

### Branch 的设计逻辑

**为什么不是一个大一统系统？** 因为不同领域的"质量"定义不同。

| | Stock | Investor | Engineer |
|------|------|------|------|
| **核心问题** | 这只股票值不值得买？ | 这个项目投不投？ | 这东西怎么工作的？ |
| **真假验证** | 财报交叉 + 价格信号 | 信源三角验证 + 尽调 | 物理实验 + 仿真 |
| **时间尺度** | 日/周/季 | 月/年 | 分钟(仿真)/天(实验) |
| **错误代价** | 赔钱 | 赔钱 | 赔钱 + 可能死人 |
| **铁律来源** | Stock 实战 + 继承共享内核 | 4 轮审计 + 8 模型交叉验证 | 待从工程实践提炼 |

每个 Branch 有自己的领域铁律（Iron Law），并继承 TRIO-Core 的共享内核（铁律 0/1/2：先算后写、信源分级、分级中断）。

### Branch 间关系

Branch 之间**不经过宪法中转**，可以直接互借方法论：
- Stock 的评分卡 → Engineer 的技术方案评估
- Engineer 的失效模式分析（FMEA） → Investor 的技术尽调
- Investor 的铁律体系 → Stock 继承共享内核

## 四、宪法 ↔ Branch：双向流动

这是 TRIO 最核心的设计原则。

### 下行（宪法 → Branch）
宪法定义通用方法 → Branch 在具体领域执行 → 宪法门禁检查交付质量

### 上行（Branch → 宪法）
Branch 实践产生教训 → 经验上浮到宪法 → 季度修订 CORE.md → 所有 Branch 自动继承

**已有先例**：
- Investor 铁律 0（先算后写）← Stock 实战中发现的汇率 10x 错误
- CORE.md「PDF 不用 Mermaid」← 2026-07-14 PDF 乱码教训
- CORE.md「终版报告格式铁律」← 蔚星科技用户两次提醒
- Stock 铁律 S2（PE 不可脱离利润结构）← 63 只分析实战

### Branch 创立标准

一个新领域成为独立 Branch 的三条硬标准：
1. **有独立的领域本体**——"质量"在这个领域的定义与其他 Branch 不同
2. **有 ≥1 个可运行的交付管道**——不只是文档，能产出实际交付物
3. **有 ≥1 个领域特有的质量门禁**——通用门禁覆盖不了的检查项

Branch 也必须有退役条件——连续 N 个周期未产生独立价值 → 合并或休眠。

## 六、已知局限

1. **情感型盲区无法被 Branch 覆盖**——三面具在同一个人的大脑里运行，共享同一个情绪系统。你爱上一个项目，三个面具都会感受到。

2. **伪多元确认风险**——当前三面具全部运行在 DeepSeek V4 Pro 单模型上，通过独立 system prompt 实现角色分化。Kimi 和 Claude 的"共识"可能只是同源噪声。目标架构：至少审计者角色迁移到独立权重模型。

3. **TRIO 自身的盲区没有自动化扫描**——目前靠手动把设计文档发给外部模型评审（就是你正在读的这份文档的原因）。

4. **单人多面具 vs 多人跨域协作——哪个更有效，没测过**。TRIO 的假设是"一个人 + 外骨骼"在某些场景下更快、更持续、更可追溯。但这只是假设。

5. **上下文预算已被违反**——CORE.md（323 行）+ CLAUDE.md（164 行）+ 项目规则 = ~689 行常驻加载，远超 L1 ≤30% 的设计上限。

6. **Branch 演化是事后合理化的**——架构文档描述的结构部分来自有机演化，不是事前设计。部分组件（Investor 5 文件 48KB vs Stock 19,826 文件 787MB）的体量差异很大。

## 七、我们想问你的

1. **宪法 → Branch 这个架构本身**——用"定义怎么思考"的内核 + 领域特定的执行分支，有没有结构性缺陷？有没有更好的模式？

2. **盲区命题有没有被浪漫化？** "不希望有盲区"在哲学上有力，但在工程上——是否过度承诺了一个系统能做到的事？

3. **单人多视角系统最确定会出错的点在哪？** 不是"可能出错"——是"如果不刻意防止，一定会出错"的那个东西。

4. **Branch 之间应该怎么通信？** 目前设计是"不经过宪法中转，直接互借方法论"。这会不会导致 Branch 间形成信息孤岛或矛盾判决？

5. **如果这是你的系统——你会砍掉什么？会加什么？**

---

> TRIO 不是答案。TRIO 是一个诚实的尝试。宪法告诉它怎么不犯错，Branch 告诉它往哪走。**但宪法和 Branch 都有自己的盲区——帮我们看见它们。**
