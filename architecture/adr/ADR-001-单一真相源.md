# @layer: evolution
# ADR-001: 建立 TRIO 数据单一真相源

## 状态

提案 | 2026-06-26 | 触发：系统架构设计方法论 Stop 1 学习

## 背景

TRIO 3.0 存在数据不一致问题：
- 公司库数量：metrics.md 说 56，DAILY.md 说 61，projects.json 说 77
- 吸收率：metrics.md 写"67%/56%"，一个指标两个值
- Run 数量：metrics.md 记录 14，DAILY.md 显示 16

根因：《系统架构设计方法论》Part 1 第 1 章指出——架构的关键决策理由未被记录，导致各模块各自维护数据副本，没有公认的单一真相源。

## 决策

**采用分层单一真相源模式：**

| 数据域 | 真相源 | 消费者（只读） |
|--------|--------|---------------|
| 公司库数量 | `projects.json`（projects 字段 + 独立公司条目） | metrics.md, DAILY.md, INDEX.md |
| Run 数量 | `.claude/history.jsonl`（实际 run 计数） | metrics.md, DAILY.md |
| 项目状态 | `projects.json`（status/last_analysis/verdict） | DAILY.md, project-context.md |
| 知识库规模 | `产出/INDEX.md`（Kimi），`knowledge/` 目录 | metrics.md |

**同步规则：**
- 消费者只能从真相源**派生**数据，不允许独立维护副本
- `mgmt.sh sync` 从真相源读取并更新所有消费者
- Post-session hook 在每次会话结束后触发 sync

**交叉验证：**
- 日进化 Layer 3 将在每次运行时交叉验证消费者数据与真相源
- 发现差异 > 5% → 标记为 🔴 并阻止消费者更新直到修正真相源

## 后果

**正面：**
- 消除"三个文件三个数字"问题
- 新模块加入时不需要猜测"哪个数字是对的"
- 自动化验证降低人工审计成本

**负面：**
- 需要一次性清理现有不一致数据
- `mgmt.sh sync` 逻辑需要重构以支持分层真相源
- 未来新增数据域必须显式声明真相源

**风险：**
- 真相源本身出错会传播到所有消费者 → 通过交叉验证缓解
- projects.json 手动更新可能滞后 → 日进化提醒未更新项目

## 合规

- [ ] `mgmt.sh sync` 重构完成
- [ ] 现有数据不一致清理完成
- [ ] 日进化 Layer 3 交叉验证逻辑就绪
- [ ] ADR 索引 `docs/adr/INDEX.md` 已更新

## 备注

灵感来源：《系统架构设计方法论》Part 1 §1.1——架构是"一组关于系统的共享理解"。
TRIO 缺少的不是数据，是关于"哪个数据是真的"这一共享理解。
