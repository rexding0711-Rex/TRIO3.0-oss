# @layer: evolution
# ADR-002: TRIO 演化四原则

## 状态

已接受 | 2026-06-26 | 触发：《系统架构设计方法论》第 1 章学习

## 背景

TRIO 3.0 有演化活动（日进化、streak、能力镜像、分层调整）但没有演化原则。每次改动修一个点，连不起来。书 §1.1 定义架构的第五要素：**"指导系统演化的原则和约束"**——TRIO 缺失。

## 决策

采用四条演化原则。所有后续架构决策必须至少不违反其中一条。

### 原则一：数字只有一个家

每个数据域只有**一个**真相源。其他地方只能引用，不能复制。

| 数据域 | 真相源 |
|--------|--------|
| 公司库数量 | `knowledge/company-library/` 目录 |
| Run 数量 | `runs/` 目录 |
| 项目状态 | `config/projects.json` |
| Kimi 产出 | `产出/INDEX.md` |

复制是腐化的开始。发现复制 → 修，不是加同步脚本。

### 原则二：加了就要跑，跑了就要看

新增一个机制（指标、镜像、挑战）必须配套三样：
1. **谁在跑**（cron/hook/手动？）
2. **跑的结果存在哪**（文件/字段？）
3. **谁在看**（日进化报告？SessionStart 问候？）

三样缺一 → 不能上线。设计不执行 = 垃圾。

### 原则三：删比加重要

加入新东西之前，先问"什么可以删"。没有删除计划的增加是熵增。

应用：14 层能力栈中 39 个"📋 规划中"——删到 10 个以内，剩下的才有资源活。

### 原则四：反向验证，不自洽不算数

任何结论、分类、判断，必须经 DeepSeek 从反面打过。通过的才能写入。自洽不是正确。

应用场景：分类决策、评分判定、叙事判断、ADR 批准。

## 后果

**正面：**
- 每次改动有原则可依，不再零散
- "一通百通"有了基础——原则通了，具体决策跟着通

**负面：**
- 原则三是逆人性的——人会本能地想"加"不想"删"
- 原则四增加决策成本——每次都要等 DeepSeek 审计

**合规检查：**
- 下次 /日进化 Layer 3 应检查：是否有违反原则的改动？
- 新 ADR 必须引用至少一条原则作为依据

## 层依赖规则（2026-06-26 追加）

```
交互层 → 场景层 → 能力层 → 知识层 → 进化层 → 基础设施层
  ↓        ↓        ↓        ↓        ↓         ↓
  单向依赖：上层依赖下层，下层不知道上层存在

mgmt.sh 是唯一跨层通道：
  任何跨层数据同步 → mgmt.sh sync
  禁止文件之间互相读内部字段
  禁止同层文件维护重复数据
```

违反即违规——日进化 Layer 3 必须标记。

## 备注

1987 年，Donald Norman 在《设计心理学》中写："约束不是限制自由——约束是让自由有意义。"

TRIO 3.14 的约束是这四条。
